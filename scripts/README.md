# scripts/

Two tools, both zero-dependency Node 18+. Neither launches Minecraft.

## new-pack.mjs — scaffold a pack that is already era-correct

```powershell
node scripts/new-pack.mjs <packFolder> --namespace <name> [--mc <version>] [--description "..."] [--force]
```

Writes `pack.mcmeta` with the version fields the target release needs
(`pack_format` up to 1.21.8, `min_format`/`max_format` from 1.21.9), the
`data/minecraft/tags/function/{load,tick}.json` entry points, and starter
functions. It also picks the era-correct folder names — `functions/` up to
1.20.6, `function/` from 1.21 — which is the single most common reason a pack
loads and does nothing. The format number comes from
`reference/data/versions.json`, never from a guess.

`--mc` defaults to the newest release; `--force` overwrites existing files.

## validate.mjs — static checker

Static checker for Minecraft Java datapacks. Zero dependencies, plain Node 18+,
never launches the game.

```powershell
node scripts/validate.mjs <packFolder> [--mc <version>] [--json <report>] [--strict] [--quiet]
node scripts/validate.mjs --self-test
```

`<packFolder>` is the directory containing `pack.mcmeta`. If you point at a
directory that contains exactly one nested pack, the validator resolves into it
and says so.

| Option | Effect |
|---|---|
| `--mc 1.21.8` | Pin the target version instead of taking it from `pack.mcmeta`. Accepts a release (`1.20.5`) — snapshots are not in the table. |
| `--json <file>` | Also write the full report as JSON: `{ packRoot, target, counts, diagnostics[] }`. Useful when the text output is long. |
| `--strict` | Treat warnings as failures (exit 1). |
| `--quiet` | Hide the INFO section. |
| `--self-test` | Validate the shipped fixtures against their frozen expectations, plus the example pack. |

Exit codes: `0` clean (or warnings only), `1` errors (or warnings with
`--strict`), `2` usage problem.

## What it checks

One run reports **everything**, sorted by file and line, so a fix pass is a batch
and not a loop.

| Prefix | Scope |
|---|---|
| `MC-JSON-*` | JSON authoring mistakes named by cause: trailing comma, comment, single quotes, BOM, full-width quotes, bad escape, control character, unterminated string, and the raw parse error with position when the text is otherwise clean. |
| `MC-STRUCT-*` | Root layout, namespace and path grammar, registry directory names (with did-you-mean), file extensions, the 1.21 plural→singular folder rename in both directions, empty namespaces. |
| `MC-META-*` | `pack.mcmeta`: required fields, the 1.21.8/1.21.9 era rules, format numbers against the table, `overlays`, `filter`, `features`. |
| `MC-FUNC-*` | Every `.mcfunction` line: leading slash, unknown command (did-you-mean), unbalanced quotes/brackets, duplicate or misordered `execute` clauses, missing `run`, unknown conditions, `data` and `scoreboard` argument shapes (these are enforced in code, not from a data table), macro rules, text-component JSON. Recurses into `execute ... run`. |
| `MC-REF-*` | Cross-file integrity: `function`, `#tag`, loot table, predicate, advancement and recipe ids resolve; function ids have no extension; unreferenced functions; load/tick tags outside the `minecraft` namespace; unguarded recursion. |
| `MC-TAG-*` | Tag file shape, namespace-less entries, self-inclusion, tags on untaggable registries. |
| `MC-REG-*` | Registry JSON minimum schema: recipes (type, per-type required keys, pattern/key agreement, result era), loot tables (type, pools, entries), advancements (criteria, triggers, display), damage types, item modifiers. |
| `MC-VERSION-*` | Syntax used that the target version does not have: item components, per-condition and per-clause gates, the 1.20.5 attribute renames, macro and line-continuation availability. |

## What it does not check

It is a text validator, not the game. It cannot know:

- whether a **vanilla** id exists (any `minecraft:...` id is accepted);
- whether a scoreboard objective is declared by another pack (it warns);
- whether an item id, block id, tag or sound is real;
- whether the pack's logic is what the user asked for;
- anything about world generation, dimensions, biomes or enchantments — those
  formats are not validated, only their folder names.
- anything inside an `overlays` sub-pack. Overlay directories live at the pack
  root and their contents are skipped entirely, so an overlay written for another
  version is not checked at all.

When it cannot decide, it stays quiet rather than guess. False positives are
treated as bugs: a report you learn to ignore is worse than no report.

## Where the knowledge lives

All version facts are data, not code, so refreshing them does not mean editing the
validator:

| File | Contents |
|---|---|
| `reference/data/versions.json` | Every release ↔ data pack format ↔ data version, the era boundary, the known format numbers. Generated by `scripts/tools/build-versions.mjs`. |
| `reference/data/commands.json` | Command names with the release that introduced them, `execute` clause lists, condition names and their gates, enum values the validator checks. |
| `reference/data/registries.json` | Registry directory table with minimum versions, the 1.21 rename map, tag registries, and the declarative rules the schema engine applies. |

Extending the validator is usually a data edit plus a rule kind, not a new check.

### Refreshing for a new Minecraft release

```powershell
# 1. re-derive research/pack-formats.json from the wiki (see its sources list)
# 2. regenerate the table the validator reads
node scripts/tools/build-versions.mjs research/pack-formats.json reference/data/versions.json
# 3. prove nothing regressed
node scripts/validate.mjs --self-test
```

## Self-test

```powershell
node scripts/validate.mjs --self-test
```

Each fixture directory under `fixtures/` is validated and its diagnostics are
compared against the frozen `fixtures/<name>.expected.json`. A missing code means
a check stopped working; an extra code means a false positive. The example pack
under `examples/` must produce zero errors. This is how the validator's own
correctness is verified without launching Minecraft.

Current fixtures: `clean-pack` (zero diagnostics), `broken-pack` (a frozen set of
deliberate defects in its `expected.json` — a missing code means a check stopped
working, an extra one means a false positive), `legacy-pack` (1.20.4, plural
folders, zero diagnostics), `modern-pack` (26.3, `min_format`/`max_format`, zero
diagnostics), `spanning-pack` (one pack covering 1.21–26.2, zero diagnostics),
`rich-pack` (macros, nested `execute`, guarded recursion, every `data modify`
form, six registry types: zero diagnostics), `rename-era-mismatch` (plural folders
on a 1.21.8 target: exactly two errors), `old-target-new-folders` (singular
folders on a 1.20.4 target: exactly two errors — the same check in the other
direction). The `examples/` packs must produce zero errors, and three scaffolded
packs (one per era) must produce zero diagnostics.
